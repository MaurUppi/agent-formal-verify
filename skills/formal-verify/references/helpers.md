# Helpers

Detailed behaviour of the verification scripts under `scripts/`. Run each helper from the target repository using `bash` or `python3` with `<skill-dir>` resolved to the installed `formal-verify` skill directory.

- **Setup helper ([`scripts/setup.sh`](../scripts/setup.sh))**: verifies the pinned TLC JAR (`tla`), checks the pinned Kani driver and bundled Rust toolchain (`rust`), and is the only helper that installs a Lean toolchain (`lean`).
- **Matrix runner ([`scripts/tlc-matrix.sh`](../scripts/tlc-matrix.sh))**: runs TLC with a matrix of constants and prints one `PASS` or `FAIL` per run with its state count, then a `SUMMARY` line with the totals. Stops each run after sixty minutes, or after the limit in `TLC_TIMEOUT` as [setup](setup.md) describes, and forwards periodic elapsed-time and `Progress(...)` updates to `stderr` during long runs. A failing run prints its error trace reduced by [`scripts/tlc_trace.py`](../scripts/tlc_trace.py) to the variables each step changed. Copy [`examples/tla-template/`](../examples/tla-template/BoundedQueue.tla) to start a spec and its matrix.
- **Lean checker ([`scripts/lean-check.sh`](../scripts/lean-check.sh))**: builds every `.lean` file in the pinned Lake project and audits every declaration of every built module. It fails on a build error, a `sorry`, a declaration that rests on an axiom beyond `propext`, `Classical.choice` and `Quot.sound`, or a `.lean` file that no Lake library owns. It checks each `<Property>.witness` theorem against its property's hypotheses, and fails on a witness that states something else, as the [Lean brief](lean-brief.md) describes. It then replays every built module, and every project module it imports, through the Lean kernel with the pin's `leanchecker`, which rejects a declaration that a command added without a kernel check. A pin without `leanchecker`, such as Lean 4.20.0, passes with the replay reported as unavailable. Use `--freeze` before the file names to record statement types and definition bodies in each model's `.statements` file before proving it. Freezing permits `sorry` and reports `FROZEN`, not a proof `PASS`. Later checks enforce those records and permit proof changes and added declarations. Given file names after the project, it checks only those files. Copy [`examples/lean-template/Model/BoundedQueue.lean`](../examples/lean-template/Model/BoundedQueue.lean) to start a model.
- **Rust checker ([`scripts/kani-check.sh`](../scripts/kani-check.sh))**: runs the pinned Kani on the crate's proof harnesses. It reports each harness's unwind bound and check count, requires a satisfied cover witness in each passing harness, rejects failed checks, and prints concrete playback tests when available. It stops each harness after five minutes, or after the limit in `KANI_HARNESS_TIMEOUT` as [setup](setup.md) describes, and fails a harness that reaches the limit with a message that names the setting. Each harness check, here or in the mutation runner, can take up to that limit, so run the command in the background or with a command timeout longer than the total. When discovery fails because code Kani compiles uses a feature newer than Kani's bundled toolchain (error E0658), the failure names that toolchain, and the [Rust brief](rust-brief.md) says what to rewrite or report. Copy [`examples/kani-template/`](../examples/kani-template/src/lib.rs) for a bounded-queue example.
- **Mutation runner ([`scripts/mutate.py`](../scripts/mutate.py))**: takes a model's `<Name>.mutations` file and applies each listed bug to a temporary copy of the model. It prints `DETECTED` or `MISSED` per mutation with what failed, `UNCOVERED` for a TLA+ property or a Kani harness in the adjacent Rust file that no mutation targets or for a public theorem in a Lean model's `.statements` file whose proof no mutation makes fail, and a `SUMMARY` line. Lean names are fully qualified. A Lean `DETECTED` line means the existing proof fails; it does not establish that the statement is false or its hypotheses can hold. A Lean mutation that changes the statement of a theorem, example or `#guard`, such as renaming a definition that the statement names, reaches no verdict, and so does a mutation that edits the text of a theorem whose proof then fails. The runner matches a failing example or `#guard` to one occurrence in the original model, so a failure in an example or `#guard` that the mutation adds, or in one that it cannot match to a single original occurrence, also reaches no verdict. So does a TLA+ mutation whose check reaches the TLC time limit, or a Kani mutation whose harness reaches the Rust checker's time limit. A mutation with no verdict stops the run with a `FAIL` line. A Lean model needs its `.statements` file before its mutations run. All three templates include a mutations file.
- **Sync helper ([`scripts/sync.py`](../scripts/sync.py))**: takes an existing model's files, the source files its header names as `--source` and the functions and shared variables it covers as `--name`, and lists what changed since the model was last synced. Its `SYNC` line gives the sync commit: the header's `Source read at` commit when `HEAD`'s history contains it, and otherwise the last commit of the model files with the reason the header's commit was not used, or `none`. For a model file that is also given as `--source`, such as a production file with its Kani harness, that fallback is the last commit that changed the code of its `#[cfg(kani)]` items and none of its other code, because a later production edit was never synced with the harness. A commit that changed only another model file, such as the TLA+ spec or the harness's `.mutations` file, does not count, since it never synced the harness. A `#[cfg(kani)]` on a field or an enum variant marks production code, not a harness. The helper reads the last 100 commits of the model files and follows each source back through its renames, so a harness commit made under an earlier name counts. It follows a rename along the renaming commit's parents, each parent of a merge that renamed a source included, so it misses a harness commit on a branch merged after the rename; the `READ` range still covers that branch's commits, and a `SYNC none` line names each such rename and its old path when a branch merged after the rename changed that path. A merge whose parents hold the source under different old paths is followed under the old path that `git diff-tree -M` finds against the first parent with one, and a `SYNC none` line names the other old paths. When git finds no rename to the source against any parent, such as when the merge grew the file below git's 50% rename similarity, the walk stops following that source there, and a `SYNC none` line names the merge and the path. When no commit it reads qualifies, the line is `SYNC none` and says whether it stopped at that limit. Each `PATH` line is a path the covered code has had since that commit: each source file through every rename since then, each file where `git grep -w -F` finds a covered name now, and each file where a commit since then added or removed a covered name as a whole word, which `git log -S` finds. A path that held the code only under another name, such as code renamed as it moved, is not found, or a path where each commit since the sync kept the number of times the name appears, such as one that replaced a mention of the name with its definition. The search leaves out each model file that is not also given as `--source`, such as a Kani harness in a file of its own. It also leaves out documents, such as `.md`, `.txt` and `.tex` files and `README` or `CHANGELOG` with no extension, and TLA+ and Lean model files, which can mention a covered name but cannot define it, unless a source path has the same extension. Other files with no extension, such as a `Makefile`, and data files, such as `.json`, `.yml`, `.toml` or `.html` files, can hold code but seldom define a covered name: the helper lists them as `PATH` lines, but a name found only in them still gets a `MISSING` line. A `MISSING` line names a covered name found in none of the files searched, with the commits since the sync that added or removed it. A name that Rust files mention only in comments and strings also gets one, and those files stay in the `PATH` lines. In other languages, such as C, JavaScript or Python, a mention in a comment or a string still counts as finding the name, since a reader of Rust's comments and strings would hide code in them. The `READ` line is the `git log -p` command over those paths, which includes commits made at an intermediate path and code that moved to another file. It exits 1 outside a git repository, for a `--source` path that no commit has, and when `git grep` fails.
- **Baseline helper ([`scripts/baseline.py`](../scripts/baseline.py))**: records what each model specifies and later names each part that changed. For TLA+ it records each run's inputs and effective checks, each reach check's selected run and inputs, and the definitions of `Spec`, of the checked and reach operators, and of the operators those reference, including the initial state. It resolves operators through sibling modules named by `EXTENDS`, including transitive imports. A definition inside a `LET` expression stays part of the definition that contains it. When a local `INSTANCE` introduces substitutions or a module has an indented definition outside a `LET`, or a column-0 definition inside one, it compares the complete local module texts with comments removed and multiline layout preserved, so edits to unrelated definitions in those modules also need review. A matrix recorded before layout or import tracking needs review and a fresh record. It shares the matrix runner's execution plan, so a check applies only to the runs after it in its section. It does not follow `Spec` into the actions it names under `[][...]_vars`, `WF_` or `SF_`, because every correction of the transcription changes them. It does follow the subscript of those forms and of `<<A>>_vars`, such as `vars`, in every definition it follows, because the subscript decides which steps may leave the variables unchanged and what fairness requires. An operator that `Spec` names outside those, such as a fairness definition, is followed into its actions. A column-0 definition whose header it cannot read, such as an infix operator, is recorded whether or not a property references it, with the operators it references. For Lean it records the `.statements` file. For Kani it records each qualified harness name with the `#[cfg(...)]` and `#![cfg(...)]` attributes that can switch it off: those on the harness, on its enclosing modules and functions, and at the top of the file, other than `#[cfg(kani)]`, and each `#[cfg_attr(<condition>, cfg(...))]` there, including one nested in another `cfg_attr`'s attribute list. A `cfg(...)` inside another attribute is not recorded, such as the one in `#[cfg_attr(docsrs, doc(cfg(...)))]`, which only labels the documentation. For a harness file that another file declares, it adds those on each out-of-line `mod <name>;` declaration that leads to the file from a crate root, on the inline modules around that declaration and at the top of the declaring file. It follows the declarations from the crate roots as rustc does, through each `#[path = "..."]` attribute and each path that a `#[cfg_attr(<condition>, path = "...")]` may set, and records that `cfg_attr` as a guard. The crate roots are the `lib.rs` and `main.rs` in the nearest directory above the file that holds either, and, in the Cargo package of the nearest directory above it with a `Cargo.toml`, `src/lib.rs`, `src/main.rs`, the `.rs` files and `*/main.rs` files in `src/bin/`, `tests/`, `examples/` and `benches/`, and each `.rs` path that a `path = "..."` or `path = '...'` line of `Cargo.toml` names. A file with neither directory above it adds nothing. A crate root is a route without a guard, since its own crate always compiles it, so a crate root that no declaration leads to adds nothing. A `lib.rs` or `main.rs` that only the nearest-directory rule finds, and that another file declares, is a module instead. A harness file that no crate root reaches fails the record. So does a `mod` declaration inside a macro, such as `cfg_if!`, or inside a function body, that may load the file, through the inline modules around it in the macro too, because the record cannot read the `cfg` around it; move the declaration out of the macro or function. The record cannot expand a macro, so a macro invocation in a reached file that may build a declaration of the file also fails the record: one outside function bodies that holds a string naming the file's name, other than `include!`, `include_str!` and `include_bytes!`, and one of a `macro_rules!` macro defined in a reached file whose body declares `mod $<name>;`, when the invocation names the file's module. So does a `name!(...)` invocation outside function bodies of a macro that no reached file defines with `macro_rules!`, such as one from another crate, when the module's name is an identifier in it that the macro may declare a module by: one outside attributes, the bodies of the functions the invocation holds, paths such as `queue::Queue`, field accesses and the `mod <name>;` and `mod <name> {` items that the record reads in macro bodies. An invocation through a path that starts with neither `crate`, `self` nor `super`, such as `builders::declare!(proofs)`, counts as one of such a macro even when a reached file defines a macro of that name. So does an invocation by a bare name written in a reached file, such as `declare!(proofs)` after `use builders::declare;`, unless every definition of that name that it may reach is one the record can read, and there is at least one. It may reach a definition earlier in the same file, outside an inline module that closes before the invocation without `#[macro_use]` or `#![macro_use]` and outside a function body that does not hold the invocation. It may also reach one in scope at every declaration or `include!` that leads to the file, one in a file that an earlier `include!` or `#[macro_use]` module declaration loads, including a module file that starts with `#![macro_use]`, one whose name a `use` item in the same module imports by a path that starts with `crate`, `self`, `super` or a module that the file declares, and, at the top of a crate root, a `#[macro_export]` macro. A bare name in a transcriber, which resolves where the macro is invoked, and a path inside the crate, such as `crate::declare!`, may reach every definition of the name. A glob import such as `use super::*;` brings in no macro. A `macro_rules!` macro counts as such a macro too when a transcriber of it passes an `ident` or `tt` metavariable of its arm to an invocation at an item position of such a macro or of one whose body declares `mod $<name>;`, such as `wrap` in `macro_rules! wrap { ($m:ident) => { builders::declare!($m); } }`, as does a macro that passes such a metavariable on to it. An invocation is at an item position when it starts the transcriber or follows a `;`, a `}` or an attribute, and braces delimit it or a `;` follows it, also inside a `$(...)` repetition, a `mod <name> {...}` body or the invocation of a macro that the record reads there. Those invocations in a transcriber, and in the invocation of a macro that the record reads, such as `wrap! { builders::declare!(proofs); }`, fail the record when they name the module as a file's own invocations do; a `$<name>` metavariable or `@<name>` rule token does not name it. Invocations inside a block or a function body in a transcriber are not read, and neither are an invocation through a metavariable, such as `$mac!(...)`, and a string in a transcriber that names the file. The record does not see a declaration that an attribute macro builds. A reached file that fails to parse fails the record when its text names the harness file's module, and is skipped otherwise. It follows each `include!("...")` item outside function bodies to the file it names, relative to the including file. As rustc does, a `mod` declaration in that file loads from the file's own directory, whatever inline modules hold the `include!`, and the guards on the `include!` item and on the modules around it are part of the route. It also follows an `include!` whose path is a `concat!` of such strings and `env!("CARGO_MANIFEST_DIR")`, which stands for the directory of the nearest `Cargo.toml` above the crate root that reaches the including file, as Cargo sets it for the crate it compiles. With no `Cargo.toml` there, such an `include!` fails the record, inside a macro or function body too. An `include!` of a file that does not exist is skipped. An `include!` whose path it cannot read, such as `include!(concat!(env!("OUT_DIR"), "/bindings.rs"))`, is not followed; it fails the record when its text names the harness file's module or file name. An `include!` inside a macro or function body is not followed either; it fails the record when the file it names is the harness file or names the harness file's module or file name. The record does not see a route through a file that an unreadable path, such as one under `OUT_DIR`, reads when the path does not name the harness file, or through a file that an unfollowed `include!` reads in turn. When more than one route leads to the file, the record holds each route as its crate root's path relative to the harness file's directory and its guards, such as `routes(lib.rs: unguarded; main.rs: cfg(feature = "slow"))`, so adding, removing or guarding any route, or moving a guard from one route to another, prints CHANGED. It also records each `kani::assume`, `kani::any_where`, `kani::cover!` and `#[kani::stub]` with its qualified owning function, including helper functions. The Rust reader supports free functions under inline modules; a Kani form in a macro, implementation or trait body, or another owner it cannot identify, fails the record. A spelling it cannot read, such as an import that renames `kani::assume`, also fails. It does not record a harness's assertions, input construction, the conditions around its assertions or calls to assumption helpers; read `git diff` for those. Create a new record after updating the helper if it reports an unsupported record format. `baseline.py move <record-file> <old file> <new file>` moves a model's record entry to the file the model moved to, reading the record alone, so a later `compare` checks the new file against what the old one specified. For a Kani harness moved into a module of its production file, add `--module <old module> <new module>`, each relative to its file, with `crate` for the file's root, such as `--module crate proofs` for harnesses that sat at the old crate's root, even when the production file is `src/queue.rs`. When the new file already has an entry, the two are merged, and an item in both fails the move. Accept a move when `compare` prints `UNCHANGED` and `git diff` shows the old file's harness lines in the new module with only their indentation changed, plus the `use crate as <name>;` line and the `#[cfg(kani)] mod proofs` lines around them. Any other change, such as an edited assertion, needs the evidence its row cites.
